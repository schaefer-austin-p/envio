Refresh button (#449)
A Refresh icon button in the message list's top bar, between Search and the menu. It is the pull's twin: core.refresh(core.refreshScope) with its ticket, gated by canRefresh, and a second tap while one runs does nothing. Only the top bar is shown (cropped); the rest of the list is as in the frames above.

  • Where: the list's TopBar actions in InboxPage, in the order Search, Refresh, Menu, in both layouts. Not in an overflow or the folders drawer: it acts on the list on screen, and a hidden entry is no easier than the gesture. In multi-select the selection bar replaces the top bar, so the button is absent there, as Search is.
  • Glyph: a three-quarter arc with an arrowhead on the 24-unit grid, 1.8 stroke, round caps, drawn like the Search and Menu glyphs. In Airmail it is the same glyph in the Airmail ink colour. It is added to the icons boards on implementation.
  • Busy: driven by the list's refreshing, so a refresh started by the pull or F5 also turns the button. The glyph rotates; no extra ring. With reduced motion it stays still and only the name changes.
  • Accessible name: "Refresh" (qsTr("Refresh")); "Refreshing" while busy. A mouse hover tooltip reads "Refresh (F5)".
  • Keys: reachable in the tab order after Search; Enter and Space activate it. F5 stays the shortcut.
  • Disabled: the same canRefresh gate as the pull; the pull indicator is hidden at the same time.
Notes

Behaviour

  • Only on the message list, with the list at the top and dragged down. No swipe actions on rows. The threshold is the existing gu(10) = 80 px of overscroll (not finger travel, which is about double), measured as originY - contentY, now one shared value.
  • The indicator fills the gap the pull opens above the first row, clipped to it. It sits under the tabs and never overlaps them.
  • Release below the threshold: the list springs back, nothing is requested. Release past it: one refresh call, the list is held at 56 px (7 gu) with the busy indicator, then returns to 0. A release while busy does nothing.
  • Pulling back above the threshold before release disarms it ((b) goes back to (a)). Release is the only trigger; crossing the line alone never refreshes.

Sizes (px at 1x, 8 px = 1 gu)

  • Threshold: gu(10) = 80 px of overscroll. Frame (b) at 88 px is 11 gu. The bindle behaviour takes it as threshold; envio passes theme.gu(10).
  • Indicator row: 32 px glyph (4 gu), 10 px gap, 14 px text (Plex Mono in Carbon, Inter in Airmail). The row follows the pull and is clipped by it, so the glyph is partly drawn on a short pull. Busy rest height 56 px (7 gu).
  • Ring: 9 units radius on the 24-unit glyph, 2.5 stroke, progress arc = pull / threshold (capped at 100 %), starting at 12 o'clock; arrow 2 stroke. Armed: solid disc with the arrow flipped up. Busy: 30 % arc, one turn per second.
  • The hold is the list's topMargin (56 px while busy), eased to 0 in 200 ms by the app when the refresh ends.

Colour tokens (Theme roles, no new colours)

  • Ring track: field. Ring progress and the armed disc: primary. Arrow on the disc: primaryText. Hint and busy text: secondary. Armed text: text at weight 600. Line under the indicator: hairline.
  • Carbon light: field #C9C6BD, primary #1E2A38, primaryText #F8F6F1, secondary #5A5D62, text #1E2A38, hairline #DAD7CE. Carbon dark: #3A4049, #E8E5DE, #15181D, #A2A5AA, #E8E5DE, #2E343C.
  • Airmail light: field #CFC6B1, primary #1F3A5F, primaryText #FBF8F1, secondary #5D6A78, text #22303F, hairline #DDD5C4. Airmail dark: #3A475A, #A9C1E3, #141C27, #A3AEBB, #ECE5D6, #2C3747.
  • The accent red is not used: it means unread and errors. The dashed threshold line and its label in (a) and (b) are annotation only and are not drawn in the app.

Accessible names and text

  • The indicator is one element with Accessible.role: Accessible.Indicator (Qt 5.15 has no Status role; StatusBar or Alert are the alternatives) and Accessible.name = the visible text: "Pull to refresh", "Release to refresh", "Refreshing" (all qsTr, domain envio.aps). The glyph is decorative.
  • Whether a screen reader announces a changed name (armed, busy) is to be verified on the phone, not promised. Nothing is announced when the refresh ends.
  • No drag is needed for assistive tech or keyboards: F5 does the same refresh (a Shortcut next to Ctrl+N, and in ShortcutLayer when wide), and the list gets an accessible press action that does the same (phone check). A visible Refresh button is a follow-up issue.

Reduced motion

  • One name throughout: reducedMotion, a plain bool property set by the app (default false; no Lomiri or Suru source for it was found, so envio sets it from its own setting if one is ever added). When true: the ring still follows the finger (direct manipulation), the arrow flip is an instant swap, the busy arc does not spin (the static arc and the word "Refreshing" carry the state), and the 200 ms settle is instant. The app owns the settle animation (a Behavior on topMargin); bindle owns none.

Accounts that cannot refresh, empty list

  • A Rust property canRefresh (derived from the accounts model: AccountRow.attention plus state "broken") decides whether the pull does anything. In scope means the open tab's account, or all accounts in the unified view. When none in scope can refresh (sign-in failed, certificate pin, unsupported, broken), no indicator is drawn, the list overshoots as plain bounce and release does nothing. No accounts at all: the same.
  • Offline accounts can refresh: the pull arms and fires, since refresh is the retry-now for an offline account (a local error is not retried by it; it needs attention instead). If nothing can run, the ack comes back at once, so busy shows for the 600 ms minimum and ends.
  • The list stays draggable when it has no rows or fewer than a page (flickableDirection: Flickable.VerticalFlick on top of DragOverBounds); the spike showed an empty list drags and holds like a full one. There is no empty-state design here.
  • Scope: a single-account tab refreshes that account (refresh(account)); the unified view refreshes all (refresh("")). The pending check and canRefresh use the same accounts.

How the busy state ends

  • Core today: multi-step runs do emit Event::AccountStatus with Syncing and then Ready, but only as text, and a refresh that needs one step may emit nothing, because Worker::report() emits only when the status after a step differs from before it. There is no per-request signal and no step queue (Worker::pick() derives one step from the per-account wants), so a generic "syncing" flag would also fire for prefetch, bodies, send and drafts and is not used.
  • New: Event::Refreshed. Every refresh produces exactly one: at once when nothing is pending in scope (no accounts, all offline, paused or needing attention, a failed step), otherwise when the pending pass ends. The foreground-resume refresh emits it too; QML ignores it unless busy.
  • QML: busy runs from release until the first Refreshed after release, never shorter than 600 ms (a no-op must not flash) and capped at 15 s as a safety net. A second release while busy does not call refresh again.
