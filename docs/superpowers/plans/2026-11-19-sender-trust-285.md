# Envio Plan: Sender trust that works for Outlook and Exchange users (#285)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** "Always for this sender" works on every account, Outlook.com and Exchange Online included, and a forged From can never earn it. Envio checks the sender's DKIM signature itself (RFC 6376), against the key in DNS, aligned with the From domain under the Public Suffix List. The receiving server's `Authentication-Results` header is believed only for a short list of named providers known to stamp every message. This closes the four holes the #278 reviews found: a forged header on a server that adds none of its own, an IP-address IMAP host, the registrable-domain approximation (`evil.duckdns.org` vouching for `victim.duckdns.org`), and strict-only alignment.

**Blocks:** Release 0.3.0. The owner (2026-11-19): "we shouldn't release until the issue is fixed in a solid and satisfying manner for outlook users".

**Architecture:** Three pure pieces in `envio-mime` (`align`: org domains from the PSL; `dkim`: tag parsing, canonicalisation, verification against keys handed in; `auth`: the provider fast path). One thin DNS TXT driver in `envio-net`. In `envio-core`: a key cache, the lookup policy (when a lookup may happen at all, a privacy rule) and the driver that runs lookups on the worker's runtime and shows the open message again when a key arrives, as `image_sizes` does today. No new screen. One QML condition changes.

**Tech Stack:** Rust (`envio-mime`, `envio-net`, `envio-core`), `ring` 0.17 (already in both locks), `base64` 0.23 (already in both locks), `psl` 2.1 (new), `hickory-resolver` 0.26 (already used by autoconfig SRV lookups), Qt 5.15 QML.

## Research (sources checked 2026-11-19)

**What Microsoft stamps.**
- Microsoft documents the inbound header as `Authentication-Results` holding `spf=… smtp.mailfrom=…`, `dkim=pass (signature was verified) header.d=…`, `dmarc=… action=… header.from=…` and `compauth=… reason=…`, citing RFC 7001, with no authserv-id in any example ([Anti-spam message headers](https://learn.microsoft.com/en-us/defender-office-365/message-headers-eop-mdo), updated 2026-08-12). The same page documents `X-Forefront-Antispam-Report` (`CIP`, `DIR:INB|OUT|INT`, `SFV`, `CAT`, an `ARC` field) and `X-Microsoft-Antispam` (`BCL`). It does not say whether intra-organisation mail gets the header, where in the header block it is placed, or whether a sender's own `Authentication-Results` is removed.
- Outlook.com writes the same id-less form on mail fetched over IMAP. A 2023 report quotes `Authentication-Results: spf=pass (sender IP is …) smtp.mailfrom=…; dkim=pass (signature was verified) header.d=…;dmarc=pass action=none header.from=…;compauth=pass reason=100` and points out the missing authserv-id and the non-RFC `action=` property. Microsoft gave no answer on the format ([Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/4635330/authentication-results-header-written-by-outlook-v), asked 2023-11-16).
- Exchange Online also puts an `Authentication-Results` header on **outgoing** mail, with the first Bcc recipient's domain as the authserv-id ([Mailhardener](https://www.mailhardener.com/blog/office-365-leaks-bcc-domains), about a 2021-05-03 report). So mail from any Microsoft 365 sender can already carry an AR header with an arbitrary, recipient-looking id. Only the topmost header may ever be read.
- `ARC-Authentication-Results: i=1; mx.microsoft.com 1; …` is written by Microsoft when mail **leaves** a tenant, and again at later hops. An IETF DMARC list post shows one real message with three Microsoft ARC sets, two `X-MS-Exchange-Authentication-Results`, two `Authentication-Results-Original` headers of unknown origin and two receiving-server AR headers, interleaved ([dmarc@ietf.org, 2024-11-13](https://go.mail-archive.com/dmarc@ietf.org/msg12376.html); Microsoft's i=2 example in [Configure trusted ARC sealers](https://learn.microsoft.com/en-us/defender-office-365/email-authentication-arc-configure)). An `mx.microsoft.com` ARC set on an inbound message may come from the **sender's** tenant, which an attacker can own, and it can only be trusted after checking the ARC-Seal cryptographically, which is DKIM-like work anyway.
- `X-MS-Exchange-Organization-*` headers are removed by the header firewall from mail that arrives from untrusted sources, and re-stamped by Exchange ([Header firewall, Exchange 2010](https://technet.microsoft.com/library/bb232136(v=exchg.140)); [Exchangepedia, 2007](https://exchangepedia.com/2007/07/header-firewall-why-spammers-cant-insert-fake-scl-and-other-exchange-organization-x-headers.html)). Microsoft documents this for on-premises Exchange; nothing current says the same for Exchange Online, or whether these headers show over IMAP.
- Outlook.com stopped basic authentication on 2024-09-16 ([Microsoft support](https://support.microsoft.com/office/outlook-and-other-apps-are-unable-to-connect-to-outlook-com-f4202ebf-89c6-4a8a-bec3-3d60cf7deaef); [heise](https://heise.de/-9767989)). Envio's Outlook users therefore all arrive through #219 (OAuth), whose client ID is still to come. No Outlook account can be tested from Envio until then.
- Microsoft 365 routing has edge cases that are hard to reason about from headers. Direct Send lets any host deliver to a tenant without authenticating; "Reject Direct Send" became generally available in 2026 and was bypassed with an empty envelope sender ([Exchange team blog](https://techcommunity.microsoft.com/blog/exchange/reject-direct-send-now-generally-available-in-exchange-online/4573787); [ReliaQuest](https://reliaquest.com/blog/threat-spotlight-one-blank-field-bypasses-direct-send-control/)). Hybrid and third-party-gateway routing makes Exchange skip DMARC enforcement (`compauth` reason 905, same Microsoft page as above).

**DKIM in the app.**
- RFC 6376 (DKIM). RFC 8301: verifiers MUST NOT accept `rsa-sha1` and MUST NOT accept RSA keys under 1024 bits; they MUST verify 1024 to 4096 bits ([RFC 8301](https://www.rfc-editor.org/rfc/rfc8301.html)). RFC 8463: `ed25519-sha256` signs the **SHA-256 hash** of the header data with PureEdDSA; `p=` is the raw 32-byte key in base64; Appendix A is a test message signed with both an RSA key (selector `test`) and an Ed25519 key (selector `brisbane`) for `football.example.com`, keys included ([RFC 8463](https://www.rfc-editor.org/rfc/rfc8463.html)).
- `ring` 0.17.14 and `base64` 0.23.1 are in both `Cargo.lock` and `qt/Cargo.lock` (via `envio-net` and `rustls`). `ring` has `RSA_PKCS1_1024_8192_SHA256_FOR_LEGACY_USE_ONLY` and `ED25519`. No `aws-lc` is in either lock.
- `hickory-resolver` 0.26.3 is in both locks with `system-config` and `tokio`; `crates/envio-net/src/autoconfig/srv.rs` already builds a resolver from resolv.conf (hosts file off, #97) and is what autoconfig uses on the phone. On Ubuntu Touch 24.04 resolv.conf points at the systemd-resolved stub; `envio.apparmor` has the `networking` policy group, which the SRV lookups already need. No DNS-over-HTTPS: the system resolver is what every other app uses, and DoH would add a third-party resolver.
- `mail-auth` 0.15.1 (Stalwart, Apache-2.0 OR MIT, 2026-10-30; [crates.io](https://crates.io/crates/mail-auth)): default features pull `aws-lc-rs`/`aws-lc-sys` (a C and CMake build for the click's cross targets); the alternative `rust-crypto` feature pulls the `rsa` crate, which has the open RUSTSEC-2023-0071 advisory, so `cargo audit` in CI fails until ignored. It depends on `mail-parser` ^1.0 while Envio has 0.11.9 (two copies), and it couples DNS I/O to verification (`MessageAuthenticator` owns the resolver), against the pure-planner rule. Rejected as a dependency; worth using offline to cross-check fixtures.
- `psl` 2.1.258 (MIT/Apache-2.0, published 2026-11-19, a new release whenever the list changes, by a daily Action; [github.com/addr-rs/psl](https://github.com/addr-rs/psl)): the list compiled into code, one dependency (`psl-types`). `publicsuffix` 2.3.0 (2024-11-14) parses a list file at run time and needs the list shipped separately. `psl` is chosen; T1 tests that private-section entries such as `duckdns.org` count as suffixes.

## Decisions

1. **Chosen: B (DKIM verified in the app) as the trust anchor for every account, with a narrow provider fast path.** A sender is verified when one DKIM signature on the message verifies against the key in DNS and its `d=` aligns with the From domain (relaxed, under the PSL), or when the account's IMAP host is in a short table of providers and their topmost `Authentication-Results` says so. Why: B rests on cryptography, not on what a server is believed to do with headers, so it is equally sound on Outlook, Exchange, Gmail and a self-hosted box, and it needs nothing from the provider. Nearly all legitimate mail is DKIM-signed today (Gmail and Yahoo have required it of bulk senders since February 2024).
2. **Rejected: A (believe the topmost id-less header when the IMAP host is Microsoft's).** It would rest on undocumented behaviour: that Exchange Online and Outlook.com stamp every delivered message, intra-tenant, hybrid, connector, gateway and Direct Send included, above anything the sender wrote. Microsoft documents none of that, the real-world header blocks are interleaved (research above), and Microsoft 365 mail already arrives with sender-side AR headers. Requiring a firewalled `X-MS-Exchange-Organization-AuthAs` next to it was considered; nothing documents that Exchange Online keeps those headers over IMAP or firewalls them. Also rejected: trusting `ARC-Authentication-Results … mx.microsoft.com` (the sender's tenant writes it), "a header above the topmost `Received`" (order is not reliable at Microsoft), and "an account whose mail never had a trusted header is unverifiable" (the attacker can send first).
3. **Rejected: the `mail-auth` crate** (see research: `aws-lc-sys` or an audited advisory, a second `mail-parser`, I/O inside the verifier). Envio writes its own verifier of about 800 lines over `ring`, checked against the RFC 8463 vector and against fixtures signed by an independent signer (T5).
4. **The provider fast path is a table of exact IMAP hosts, not a domain rule.** `PROVIDERS: &[(imap_host, &[authserv_id_suffix])]`: `imap.gmail.com` → `mx.google.com`; `imap.fastmail.com` → `messagingengine.com`; `imap.mail.me.com` → `icloud.com`, `apple.com`; `imap.mail.yahoo.com` → `yahoo.com`. The rule "the id's registrable domain equals the IMAP host's" goes away: it is exactly what lets a forged header through on a self-hosted server that stamps nothing, and on an IP host (`10.0.0.1` gave `0.1`). Self-hosted, IP-address and Microsoft hosts never take the fast path; they use DKIM. Why keep it at all: it costs no DNS lookup, and it covers mail the provider authenticated by SPF only. An entry needs a captured header from that provider (T0); an entry without one is removed. Microsoft is not in the table (decision 2). Owner decision 2026-11-19 (#285): keep the fast path (owner decision O2 below).
5. **Alignment is DMARC's relaxed rule with the PSL** (RFC 7489 section 3.1.1): `org_domain(d) == org_domain(from_domain)`, with `org_domain` from `psl` including the private section. A host that is an IP literal, has a single label, or is itself a public suffix has no org domain and aligns with nothing. The same rule serves DKIM (`d=`) and, in the fast path, `header.d`, `smtp.mailfrom` and `header.from`.
6. **Exactly one From header, with exactly one mailbox, whose domain is the one shown.** A message with two `From:` fields (the classic DKIM attack: the signature covers the lower one, the reader shows the upper one) or a From with several mailboxes is never verified, by either path. The domain compared is parsed from the single raw `From:` field and must equal the domain of `header.from_address` that the reader shows.
7. **A DNS lookup happens only when its answer can change what the user sees, and only for a sender the user already trusts with images.** A DKIM key lookup can work as a read receipt: a sender who signs each message with its own selector learns from the query for `<selector>._domainkey.<domain>` at its name server that the message was opened, when, and through which resolver. That is the very leak image blocking exists to stop. So the core looks up keys only when (a) images are blocked by default, (b) the sender's address is in `images_from` (the user chose "Always for this sender"), (c) the fast path did not already verify, and (d) the message has a DKIM signature that is aligned, supported and covers From. Contacts alone never cause a lookup. Owner decision 2026-11-19 (#285): lookups only for allowed senders (owner decision O1 below).
8. **"Always for this sender" shows when the message can be checked, not only when it is already verified.** With decision 7 a message from a sender who is not yet allowed is never looked up, so it cannot be verified in advance. The banner offers "Always for this sender" when the message is verified **or** carries a DKIM signature that could verify it (`sender_checkable`, decided from the message alone, no network). Tapping it allows the address and loads this message's images (as "Load images" does, so it leaks nothing new); later messages from that address load images only when their own signature verifies. Safety does not depend on the button: the allow never applies to a message that does not verify. Unsigned mail outside the fast path cannot be allowed, as today. Owner decision 2026-11-19 (#285): show the button for checkable mail (owner decision O3 below).
9. **Verification rules** (RFC 6376 unless noted): `v=1`; `a=rsa-sha256` or `ed25519-sha256` only (`rsa-sha1` is rejected, RFC 8301); `h=` must include `from` and `content-type` (without `content-type` a replayed signed mail could carry an added, unsigned `Content-Type: text/html` and turn signed text, quoted attacker text included, into HTML with images; when the message has no Content-Type field, listing it in `h=` signs its absence, RFC 6376 5.4); `i=`, when present, is `d` or a subdomain of it; `x=` in the past is a failure; a signature with `l=` shorter than the canonicalised body is a failure (otherwise content, images included, could be appended after the signed part); the key record's `p=` empty (revoked), `t=y` (testing: RFC 6376 says treat as unsigned), `s=` without `email` or `*`, or `h=` not listing `sha256` are failures; with `t=s` the `i=` domain must equal `d`. At most 5 signatures are tried and at most 3 keys looked up per message. **Known limit:** a body cached as `BodyState::Partial` (large messages) cannot pass, since its body hash will not match: such a message never verifies through DKIM and its images stay blocked until the user taps Load (the provider fast path, which needs no body, still works). This fails closed and is written into the spec (T9).
10. **Results:** pass is cached in memory per open message; keys are cached in memory, bounded (256 entries), for the record's TTL clamped to 1 minute to 1 hour; "no such record" is cached 5 minutes; a timeout or server failure is not cached, but the name is remembered for the open message (`Shown.failed`, T7, carried across re-renders) and not looked up again until the message is opened again, so a resolver that is down costs one lookup per name per open, never a loop. Nothing is written to SQLite (no migration). An old message whose key was rotated away becomes unverified and its images stay blocked: safe, and the user can still tap "Load images". Offline nothing can be looked up, and remote images could not load anyway.
11. **The PSL is refreshed at each release.** Dependency bots are security-only (memory: dependency-bots-security-only), so `psl` is not bumped automatically. `auditing-before-launch` for a release runs `cargo update -p psl` in both locks. A stale list errs on one side only for new private suffixes (two tenants of a new shared suffix could align); the public-suffix entries that matter for mail rarely change.
12. **No DNSSEC.** Envio trusts the system resolver as every receiving MTA that checks DKIM does. Someone who can forge DNS answers to the phone can make a forged message verified, and the result is a remote image loading for a sender the user allowed. The same attacker can already see every connection the phone makes.

**Produces:**
```rust
/// The organisational domain (public suffix plus one label), lowercased,
/// trailing dot removed; None for an IP literal (v4, or v6 with or without
/// brackets), a single label, an empty string or a public suffix itself.
pub fn org_domain(host: &str) -> Option<String>;
```

### T3: DKIM tag lists and key records (envio-mime)

**Files:** new `crates/envio-mime/src/dkim/mod.rs` (module doc, re-exports), `dkim/tags.rs`, `dkim/key.rs`, `crates/envio-mime/Cargo.toml` (`base64 = "0.23"`).

**Produces:**
```rust
pub(crate) enum Algorithm { RsaSha256, Ed25519Sha256 }
pub(crate) enum Canon { Simple, Relaxed }
pub(crate) struct Signature {
    pub algorithm: Algorithm,
    pub header_canon: Canon, pub body_canon: Canon,
    pub domain: String,            // d=, lowercased
    pub selector: String,          // s=
    pub signed_headers: Vec<String>, // h=, lowercased, in order
    pub body_hash: Vec<u8>,        // bh=, decoded
    pub signature: Vec<u8>,        // b=, decoded
    pub body_length: Option<u64>,  // l=
    pub agent: Option<String>,     // i=
    pub expires: Option<u64>,      // x=
}
impl Signature {
    /// `content-type` is in `h=` (decision 9; checked by T5, not here).
    pub fn signs_content_type(&self) -> bool;
}
/// RFC 6376 3.2 tag-list: `tag=value` pairs split on `;`, whitespace
/// (FWS) around tags and values removed, inside base64 values removed.
/// None on a duplicate tag or a malformed pair.
pub(crate) fn tag_list(value: &str) -> Option<Vec<(String, String)>>;
/// None when a required tag is missing, `v` is not 1, `a` is unsupported
/// (rsa-sha1 included), `h` lacks `from`, `i` is outside `d`, or a value
/// does not decode. (`h` lacking `content-type` still parses; T5's
/// candidate filter rejects it, so the RFC 8463 vectors stay usable.)
pub(crate) fn signature(header_value: &str) -> Option<Signature>;

pub(crate) enum PublicKey { Rsa(Vec<u8> /* PKCS#1 RSAPublicKey DER */), Ed25519([u8; 32]) }
```

**Tricky part, full code:** DKIM `p=` for RSA is a SubjectPublicKeyInfo (RFC 6376 3.6.1), while `ring` wants the inner `RSAPublicKey`. Some domains publish the bare `RSAPublicKey`. Accept both:

```rust
/// The RSAPublicKey inside a SubjectPublicKeyInfo for rsaEncryption, or
/// `der` itself when it already is a bare RSAPublicKey (a SEQUENCE of two
/// INTEGERs). Strict DER lengths; nothing after the outer SEQUENCE.
fn rsa_public_key(der: &[u8]) -> Option<&[u8]> {
    const RSA_OID: &[u8] = &[0x06, 0x09, 0x2a, 0x86, 0x48, 0x86, 0xf7, 0x0d, 0x01, 0x01, 0x01];
    let (outer, rest) = tlv(der, 0x30)?;
    if !rest.is_empty() {
        return None;
    }
    // Bare RSAPublicKey: SEQUENCE { INTEGER n, INTEGER e }.
    if let Some((_, after_n)) = tlv(outer, 0x02)
        && let Some((_, after_e)) = tlv(after_n, 0x02)
        && after_e.is_empty()
    {
        return Some(der);
    }
    // SPKI: SEQUENCE { SEQUENCE { OID rsaEncryption, NULL? }, BIT STRING }.
    let (alg, rest) = tlv(outer, 0x30)?;
    if !alg.starts_with(RSA_OID) {
        return None;
    }
    let (bits, rest) = tlv(rest, 0x03)?;
    if !rest.is_empty() {
        return None;
    }
    let (unused, key) = bits.split_first()?;
    (*unused == 0).then_some(key)
}

/// One DER TLV with the expected tag: (contents, the bytes after it).
fn tlv(input: &[u8], tag: u8) -> Option<(&[u8], &[u8])> {
    let (&t, rest) = input.split_first()?;
    if t != tag {
        return None;
    }
    let (&first, rest) = rest.split_first()?;
    let (len, rest) = match first {
        n if n < 0x80 => (usize::from(n), rest),
        0x81 => {
            let (&n, rest) = rest.split_first()?;
            (n >= 0x80).then_some((usize::from(n), rest))?
        }
        0x82 => {
            let (bytes, rest) = rest.split_at_checked(2)?;
            let n = usize::from(u16::from_be_bytes([bytes[0], bytes[1]]));
            (n >= 0x100).then_some((n, rest))?
        }
        _ => return None, // keys over 64 KiB are not DKIM keys
    };
    rest.split_at_checked(len)
}
```

**Tests:**
- `tag_list`: folded value with tabs and CRLF; base64 `b=` with embedded whitespace decodes; a duplicate tag → None; a trailing `;` is fine; an empty value (`b=`) is kept.
- `signature`: the RFC 8463 Appendix A signatures parse (both); `a=rsa-sha1` → None; `h=subject:date` (no From) → None; `h=from:subject` (no content-type) → Some, with `signs_content_type()` false; `i=@other.example` with `d=football.example.com` → None; `i=@sub.football.example.com` → Some; `v=2` → None; missing `bh` → None.

**Tricky part, full code:** the two algorithms take different inputs (RFC 8463: Ed25519 signs the SHA-256 of the data; `ring`'s RSA verifier hashes the data itself).

```rust
fn check(alg: Algorithm, key: &PublicKey, data: &[u8], sig: &[u8]) -> bool {
    use ring::signature::{self, UnparsedPublicKey};
    match (alg, key) {
        (Algorithm::RsaSha256, PublicKey::Rsa(der)) => {
            UnparsedPublicKey::new(&signature::RSA_PKCS1_1024_8192_SHA256_FOR_LEGACY_USE_ONLY, der)
                .verify(data, sig)
                .is_ok()
        }
        (Algorithm::Ed25519Sha256, PublicKey::Ed25519(raw)) => {
            let digest = ring::digest::digest(&ring::digest::SHA256, data);
            UnparsedPublicKey::new(&signature::ED25519, raw)
                .verify(digest.as_ref(), sig)
                .is_ok()
        }
        _ => false, // k= does not match a=
    }
}
```

`ring` rejects RSA moduli under 1024 bits by itself (RFC 8301); a test proves it.

## Owner decisions (2026-11-19, #285)

The owner answered "Yes to all 3" on 2026-11-19: all three recommended options are chosen. They are binding for this plan.

O1. **DKIM keys are looked up only for senders on the "Always for this sender" list, and only while their message is open** (decision 7). Then a sender learns nothing from DNS that images would not already tell them. Accepted cost: contacts who are not on the list are verified only through the provider fast path, so `sender_known` stays false for them on Outlook and self-hosted accounts. Rejected: a lookup for every signed message on open (verdict known up front, but a sender who uses one selector per message gets a read receipt from their name server).
O2. **The provider fast path stays** (decision 4), for Gmail, Fastmail, iCloud and Yahoo, each limited to providers whose real headers T0 captured. It saves a lookup and covers mail those providers authenticated by SPF alone. Rejected: DKIM only everywhere (simpler, but mail without a DKIM signature could never be allowed on any account).
O3. **"Always for this sender" shows on signed mail that is not yet verified** (decision 8): whenever the message has a DKIM signature that could verify it. Tapping it allows the address and loads this message's images, as "Load images" does. Rejected: the button only on already-verified mail (with O1, Outlook and self-hosted users would never see it).
