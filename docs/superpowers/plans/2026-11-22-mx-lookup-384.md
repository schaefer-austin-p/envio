# Envio Plan: Microsoft 365 on custom domains, by MX lookup (#384)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** On the "Other" wizard path, a custom domain whose mail is on Microsoft 365 (found by a DNS MX lookup during Detect) no longer ends at a password step that cannot work. The email step shows "This mail is on Microsoft" with "Sign in with Microsoft"; where Microsoft sign-in is off, it shows the #381 refusal with the domain filled in.

**Spec and design:** `docs/superpowers/specs/2026-11-21-envio-graph-backend-design.md` (Wizard section: "Other: auto-detect, plus the MX lookup (#384)"; the tenant decides Graph or IMAP after sign-in). Boards: `docs/design/carbon-provider.html` frame "Other: the mail is on Microsoft" (and its caption), `docs/design/carbon-ms-refused.html` frame "Follow-up: #384" (and `airmail-ms-refused.html`). Executors read these; this plan does not repeat them. Where this plan and the issue text differ, **Decisions** wins.

**Builds on** PR #421 (`origin/p7-provider-step`): `Worker::provider_of`, `start_oauth(email, account, kind)`, `route.rs` tenant routing, the provider step and `wizardFlow.js`. P1 does not need #421; P2 and P3 do (rebase onto master once #421 merges).

## Global Constraints

- Dependencies point one way: ui → core → sync → net, store, mime. Logic in Rust; QML only shows the banner and calls the core. `unsafe` only in `qt/`.
- No new crate. hickory-resolver 0.26 (already in envio-net, `system-config`, `tokio`) has `mx_lookup`; check with `cargo tree -i hickory-resolver` and `cargo check`, nothing heavier. Files around 300 lines; `autoconfig/mod.rs` is 150 now, so new code goes in new modules.
- Only the domain leaves the device, as with today's lookups; the lookup goes to the system resolver (see Decision 2). No real DNS in any test: all tests use a fake `Lookups`.
- User-facing text: gettext in Rust (`tr`, `fill`, domain `envio.aps`), `qsTr()` in QML; run `cargo make pot` after string changes (do not commit a date-only pot refresh).
- Tests: single-crate in `crates/<crate>/tests/`; cross-crate in `envio-e2e`.
- Design rule: a screen change gets its mockup first (T3) and a separate-agent conformity check before the QML is built; after the build, a design-review round with screenshots against the board.

## Decisions

Taken on the owner's behalf after reading the code; the owner may override. No open owner decision (Decision 2 explains why DoH is not proposed).

1. **Lookup = the existing system resolver, `Lookups::mx`.** `Internet` already builds one `TokioResolver` from resolv.conf for SRV (`dns.rs::resolver()`, hosts file off, 4 s per attempt, 2 attempts); hickory's `mx_lookup` uses the same one. No new dependency, no new code path for UT's resolver setup (SRV and TXT already work there; whether detect's resolver works on a phone with a broken resolv.conf is checked in T4, which is why the limit is 5 s).
2. **No DoH.** The domain already goes to the system resolver for SRV (and to the ISPDB, the provider host and the well-known URL). MX adds one more query type to the same recipient, so it discloses nothing new. DoH would add a third-party service seeing every domain the user types, plus an HTTP client path and a service choice: not needed, so not proposed. (If the owner ever wants DoH, it is a separate issue and an owner decision: options would be none, Cloudflare/Quad9-class public DoH, or a self-hosted DoH on the Scaleway box.)
3. **AppArmor: nothing.** DNS over UDP/TCP 53 is under the `networking` policy group that `envio.apparmor` already has; SRV and TXT run on the same path. No manifest or policy change.
4. **Timeouts.** `MX_TIMEOUT = 5 s` in `autoconfig/mx.rs` (one resolver attempt of 4 s plus margin, so the second attempt is cut off: one lost UDP packet on a lossy network gives a false negative, "not Microsoft", which is accepted because a false negative only costs today's flow; a dead resolver must not make every Continue wait, since a file hit used to return in under a second; the limit applies to the MX side only), not the resolver's full two-attempt 8 s. The MX query runs concurrently with the file fetches and SRV, and each side is limited separately: `futures::join!(timeout(budget, find), timeout(min(mx_limit, budget), lookups.mx(domain)))` (`futures::join!`: envio-net's tokio has no `macros` feature). So the whole stays within `DETECT_TIMEOUT` and an MX timeout cannot discard a settled `find` (nor the reverse). Continue waits for the slower of the two: at most 5 s more than today when the resolver is dead or slow, nothing more when it answers.
5. **Offline / failure = "not Microsoft".** `mx` returns an empty list on any failure (timeout, SERVFAIL, NXDOMAIN, no resolver), the same rule as `srv`. Detect then proceeds exactly as today (files, SRV, guess). A false negative costs what it costs today (a password step); a false positive is the bad case, so matching is strict (Decision 5).
6. **Which hosts count.** Pure `hosting_of(&[MxRecord]) -> Hosting` decides. Only the most-preferred MX records (lowest preference value) count: the answer is `Microsoft365` when there is at least one such record and **every** one of them has a host of the form `<one label>.mail.protection.outlook.com` (case-insensitive, trailing dot ignored; `contoso-com.mail.protection.outlook.com`). A migrating domain with mixed top-priority records, a gateway first (Mimecast, Proofpoint, an on-prem relay) or the null MX (`.`) gives `Unknown`. Not matched on purpose: `*.olc.protection.outlook.com` (consumer Outlook.com/Hotmail, whose domains `provider_kind_for` already knows and whose custom domains are not a supported path), the sovereign clouds (`*.mail.protection.outlook.us`, `*.mail.protection.office365.us`, `*.mail.protection.partner.outlook.cn`: different login authorities than the app's provider), and `autodiscover.<domain>` CNAME (the issue's optional second signal: it would catch domains behind a gateway, but costs another lookup and a second false-positive source; left for a follow-up if users report gateways). Microsoft's DNSSEC form, `<domain>.mx.microsoft`, **is included**: exactly one label before `.mx.microsoft`. The implementer confirms the exact shape in Microsoft's Exchange Online DNSSEC documentation before coding it; if the docs show another shape, use the documented one and say so in the PR. Tests cover both forms.
7. **A false positive is possible by design** (EOP in front of an on-prem server; DNS is unauthenticated). Harm is bounded: the user sees Microsoft's own sign-in, the `tid` and email checks in `oauth.rs` refuse an account that is not the typed address, and nothing is saved. So the frame keeps a way out: **"Set up manually" stays visible** in the Microsoft frame (the board's refused frames hide it, so T3 updates both Microsoft frames, light and dark, Carbon and Airmail, and the conformity check covers them). Manual setup is not refused for these domains: `connect` refuses by `provider_kind_for(address)` only, which is None for a custom domain.
8. **The verdict wins over found settings.** When `Hosting::Microsoft365`, Detect's answer is the Microsoft frame whatever `found` says (ISPDB or SRV settings for such a domain cannot work with a password: Exchange Online has no basic-auth IMAP). `found` is still computed (cost of concurrency) and dropped. Verdict reaches the worker as data; the worker decides.
9. **What the worker does** on `Hosting::Microsoft365` (in `Worker::detected`, after the stale-ticket check): if `provider_of(ProviderKind::Microsoft)` exists, emit new `Event::MailOnMicrosoft { email, title, text }`; otherwise emit the existing `Event::SetupRefused` with the #381 refusal text carrying the domain (one string, `{domain}`). No `Detected`, so the wizard stays on the email step ("after Continue, cleared on edit", as the boards say).
10. **Sign-in kind.** The wizard starts `start_oauth(email, None, Some(ProviderKind::Microsoft))`: a custom domain on EOP is a work tenant. (`kind` must be passed: `provider_kind_for` is None for these addresses.) Because `start_oauth` treats a passed kind as a pick (`picked = kind.is_some()` in fc12f4c), a personal tenant gets the mismatch question frame ("This is a personal account") before the second sign-in: kept on purpose, it is the board's "the mismatch frame covers a wrong guess" and needs no hint plumbing. A personal tenant is caught by `route.rs` (`Other { personal: true }`), which shows the mismatch frame and runs the one second sign-in with Graph scopes. No change to `route.rs`.
11. **Scope.** #384 is the Microsoft 365 verdict only. The board frame "Other: the MX lookup found settings" (a provider name such as Fastmail from MX) is **not** in the issue and needs a table of MX-to-provider names; it is left for a follow-up issue (log it), and `text::setup::found_by` is unchanged. Note its caption says the banner shows "before Continue"; lookups never run before Continue (the ISPDB note promises this), so any follow-up reads it as after Continue.
12. **The ISPDB note gets one clause** so the privacy text stays true: it names the ISPDB and the mail provider but not DNS, which SRV already used and MX now also uses. New text: "…asks the Thunderbird configuration database, your mail provider and the DNS records of your domain. Only the part of your address after the @ is sent." The board frames that show this note are updated with it (T3).
13. **A known consumer domain typed under "Other" goes straight to Graph** (coordinator's addition, vs #421 at fc12f4c). Today `detect_with_provider` and `start_oauth`'s fallback both use `provider_kind_for`, which gives `ProviderKind::Microsoft` (IMAP scopes) for every Microsoft domain; a consumer account then fails `route.rs` (`Other { personal: true }`) and the user sees the browser twice. Fix: a new pure `pub fn consumer_microsoft_domain(domain: &str) -> bool` in `crates/envio-net/src/oauth/provider.rs`, beside `microsoft_domain` and the `OUTLOOK`/`HOTMAIL`/`LIVE` tables it already owns (the list lives there, not in core's `known.rs`, which holds the app-password servers and cannot own a list net's `provider_kind_for` needs). It is true for `outlook.*`, `hotmail.*`, `live.*` (the tables), `msn.com` and `windowslive.com`; false for `office365.com`, `*.onmicrosoft.com` and everything else: exactly the narrow list the spec gives for #342 eligibility, so #342 reuses it rather than keeping a second copy. `provider_kind_for` keeps its answer and its tests (the #381 refusal and work domains rely on it). New `Worker::default_kind(email) -> Option<ProviderKind>` in `worker/oauth.rs`: `MicrosoftGraph` when `consumer_microsoft_domain` and `provider_of(MicrosoftGraph)` is set up, else `provider_kind_for`. `detect_with_provider`, `refuse_microsoft` and `start_oauth`'s `kind.or_else(..)` use it, so the offer, the sign-in and the saved account are Graph from the first sign-in. Where Graph is off (no client ID or flag), behaviour is today's (IMAP kind). The double sign-in remains only for a personal account on a custom domain (the MX path of Decision 10, an MX hit on a personal tenant; with no MX hit no sign-in is offered at all), where the tenant routing is the safety net. `refuse_microsoft` gates on `provider_of(default_kind(email))`, the same per-kind rule as today, so a consumer address is refused only when neither Graph nor IMAP sign-in is set up; manual `Connect` behaves as today. The Graph offer in `detect_with_provider` carries `servers` empty (the provider's IMAP/SMTP hosts are unused for Graph), the sign-in step shows no servers line and no "Edit servers" when `servers` is empty, and its text is `text::oauth::found("Microsoft")` (`provider_name` already maps both kinds to "Microsoft"). A `tid` that disagrees (a work account on a consumer-looking domain cannot exist, but an old alias might) is still caught by `route.rs`.
14. **Bindle candidates: none.** The banner is a `NoticeCard` with two buttons on an envio wizard page; nothing reusable beyond it. If a second app needs a card with actions, `NoticeCard` is the candidate then.
